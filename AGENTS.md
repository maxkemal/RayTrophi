# Workspace instructions

- Agent verification screenshots are temporary artifacts, not repository assets. Store them in an ignored temporary directory (prefer `docs/dev/.captures/`), never commit or force-add them, and delete the screenshots you created when the task finishes. Preserve intentional product/documentation artwork outside this temporary capture workflow.

- Do not run C++ project/application builds (including MSBuild, CMake build, or IDE builds). The user performs C++ builds.
- Shader compilation and deployment are Codex's responsibility (user instruction, 2026-11-09): compile affected shader variants, validate outputs, and copy them to the source/runtime shader folders. Keep any new shader registered in the bulk compilation scripts; avoid recompiling unrelated shaders when only a subset changed.
- Do not launch the RayTrophi Studio application for verification unless the user explicitly asks in that turn.
- Codex may perform read-only inspection, static audits, and non-build source checks, then hand the exact build/test checklist to the user.
- The canonical scene geometry is the flat `TriangleMesh` / DNA SoA representation. New features must read and mutate that flat data path directly; do not use per-face `Triangle` facade collections as scene geometry sources or authoritative state.
- Template, startup, welcome-screen, guided-scene, or related UX work must follow `docs/dev/TEMPLATE_HUB_UX_ROADMAP.md` as the canonical product direction. Preserve the viewport-first UI, reuse the existing left context rail/right contextual dock/bottom editor structure, and avoid introducing a large permanent shelf.
- Do not add feature implementation to an existing source file that is over 2000 lines. Create focused new `.h/.cpp` modules instead; an over-2000-line file may receive only the smallest necessary include, declaration, call, registration, or other integration wiring.
- Every new user-facing system or authoring capability must expose its canonical operations through both the scripting API and IPC. UI, scripting, and IPC must call the same underlying service/core logic; do not create UI-only implementations or duplicate business logic in bindings. A feature is not complete until its script and IPC surfaces, validation/error semantics, and relevant tests/documentation are delivered together.
- Keep new and edited C++ code readable: use 4-space indentation, aim for 100-column lines, and expand functions, conditions, loops, and statements onto properly indented lines rather than compressing them into long single lines. Keep formatting changes focused on the requested files.
- Parallel agents (Codex and Claude Code) work in this same working tree and cannot message each other. The shared channel is `docs/dev/AJAN_KOORDINASYON.md`: read it before touching any shared file; list the files you are working on in its §1 when you start and remove the row when done; record any change that can break the other agent's build or run (shader binding count / push-constant size, `SimulationComputeVulkan.cpp` registry rows, widely used struct layouts, IPC field meaning) in §2; record work waiting for a build (incremental or full) in §3; put ideas, questions and division-of-work proposals in §4 and answer under the item. Re-read shared files fresh before editing, never `git add -A`, and do not reformat files another agent is working on. The board does not replace the user's approval.
- For live application verification, use the external named-pipe client in `scripts/test/rt_ipc.py` while RayTrophi Studio is open. Run IPC probes from a separate terminal/process, never from the application's embedded script workspace because that blocks the main thread. In the Codex sandbox, named-pipe access may fail with Windows error 5; rerun the Python IPC probe with the required sandbox escalation instead of inventing another transport or assuming the listener is down.
